# Week 4 observation

## Task 1
- Bloom filter의 비트는 0→1로만 바뀌고 다시 0이 되지 않는다. 넣은 원소의 k개 비트는 영원히 1로 남으므로 false negative는 구조적으로 불가능하다.
- m=8,192, k=5, n=800에서 §4.4.2 예측값 (1−e^(−kn/m))^k는 0.860%, 없는 원소 20,000개로 잰 값은 0.865%였다. 해시 k개를 blake2b 다이제스트의 겹치지 않는 8바이트 조각에서 뽑아 서로 독립으로 만들었기 때문에, 독립을 가정한 식이 그대로 맞았다.
- Flajolet-Martin은 해시 64개의 R을 평균한 뒤 2^평균R에서 편향 0.333비트를 빼서 썼다. 0.333비트는 Flajolet & Martin(1985)의 E[R] ≈ log₂m + γ/ln2 − 1/2에서 온 값이다. 같은 스트림에 시드 10개로 비교했다(`--compare`).
  - 2^R 평균은 2.06~10.67배였다. §4.5.3의 그룹 평균→중앙값은 8개씩 묶으면 1.72~7.42배(2배 이내 2/10)였다. 교재 권장(그룹 크기 ≥ log₂m ≈ 14)에 맞춰 16개, 32개씩 묶으면 2.32~7.71배, 2.06~10.67배(둘 다 0/10)로 오히려 나빠졌다. 2^R은 꼬리가 무거워(P(2^R > t) ≈ m/t) 그룹이 클수록 평균이 가장 큰 값에 더 끌려가기 때문이다.
  - 중앙값은 0.82~1.23배로 통과했지만, 결과가 항상 2의 거듭제곱(또는 이웃한 둘의 평균)에 묶인다.
  - 지수 R을 평균하는 쪽이 0.80~1.32배로 가장 안정적이었다.
- reservoir sampling에서 길이를 몰라도 되는 곳은 `j = rng.randrange(i)`와 `if j < k` 두 줄이다. i번째 원소를 k/i 확률로 받아들이면 "지금까지 본 i개가 각각 k/i 확률로 남아 있다"는 불변식이 매 단계 유지된다. 그래서 스트림이 언제 끝나든 그 순간의 표본이 정답이다.

## Task 2
- 내 컴퓨터(i5-12450H, RAM 16 GB, Windows 11, Python 3.11.2, Chrome·Claude·PowerShell로 약 1.2 GB 사용 중)에서 정확한 방법이 견딜 수 없어진 크기는 'n = 1억'(서로 다른 원소 약 3,670만)이었다. 먼저 바닥난 것은 '메모리'였다. `--exact-only`로 실행했는데 시스템 메모리가 최대 약 14 GB(90% 이상)까지 올라가 직접 중지했고, 시간은 같은 비율이면 5~6분 정도라 아직 견딜 만했다. n = 2,500만에서 tracemalloc이 잰 원소당 89바이트로 계산하면 3.3 GB면 충분했어야 하는데, 실제로는 다른 프로그램 1.2 GB를 빼고도 약 12.8 GB, 서로 다른 원소당 약 350바이트로 4배 가까이 찼다. tracemalloc의 할당별 추적 정보와 set 확장 시 테이블이 이중으로 존재하는 것이 원인으로 보인다(미검증). 따라서 tracemalloc 값만으로 한계를 외삽하면 크게 낙관적이 된다. 자세한 표는 `limits.md`에 있다.
- A4는 성립했다. set 메모리는 n이 4배가 될 때 약 4배로 'n에 비례'했다. n = 2,500만의 818.2 MB는 문자열 60바이트 × 918만 = 551 MB와 해시 테이블 2²⁴칸 × 16바이트 = 268 MB의 합(819 MB)과 정확히 맞는다. FM은 n이 250배가 되는 동안 4,428 → 4,430바이트로 '상수'였다. 해시 개수(정수 64개)가 정하기 때문이다. 시간은 둘 다 선형이지만 FM이 원소당 61 µs로 set(3.3 µs)보다 훨씬 느렸다. 두 값 모두 스트림 생성을 포함하므로, FM이 해시 64개 계산에 원소당 약 57 µs를 더 쓴 셈이다. 그래서 n = 2,500만에서는 FM이 25분으로 오히려 먼저 지루해졌다.
- FM 비율은 1.14 → 0.86 → 0.96 → 0.98 → 0.95로 n과 상관된 추세가 없다. 오차는 n이 아니라 해시 개수가 정하며(64개면 약 ±17%), 이것이 평평한 메모리 곡선의 대가다. "오늘 방문한 순사용자 수"에 이 정도 오차는 트래픽 규모 파악이나 급변 감시에는 충분하다. 하지만 사용자 수 기준 과금이나 몇 % 차이를 보는 A/B 테스트에는 부족해서, HyperLogLog나 정확한 집계가 필요하다.

## Task 3
- 해시 개수 k만 바꿨다. FP = (1−e^(−kn/m))^k에서 p = e^(−kn/m)로 두면 ln FP = −(m/n)·ln p·ln(1−p)이다. 이 식은 p와 1−p에 대칭이라 p = 1/2에서 최소가 된다. 따라서 k = (m/n)·ln2 = 10 × 0.693 = 6.93이고, 정수로 'k = 7'을 골랐다. 베이스라인은 k = 1이라 1 − e^(−0.1) = 9.52%로 예측되고, 실측 9.511%와 맞는다. `memory_bits()`는 실제로 할당한 비트 배열 크기(80,000)를 보고한다. k와 해시 키는 `NaiveFilter`의 seed와 같은 종류의 설정값이라 세지 않았다.
- R6: 10비트/원소의 하한은 (1/2)^(10·ln2) = 0.6185^10 ≈ '0.819%'다. 실측은 0.791%(1,582/200,000)로 91.7% 줄어 strong이었다. 하한보다 살짝 낮은 것은 표본 오차(표준편차 약 0.02%p) 범위 안이다. 삽입 후 1인 비트 비율이 0.502로, 최적 조건이 실제로 만들어졌다. 최적점 양쪽을 비교하면 k=6(−0.93)은 0.859%, k=8(+1.07)은 0.797%였다. 더 멀리 떨어진 k=8이 더 좋으므로, 최적점 근처에서는 k가 작은 쪽이 더 손해다.
- n을 모르면 k와 m을 정할 근거가 사라진다. 너무 적게 잡으면(실제 n이 추정의 2배인데 k=7) FP가 13.8%로 뛴다. 같은 메모리에서 k=3이었다면 9.2%였다. 너무 많이 잡으면 비트 대부분이 0으로 남아 메모리를 낭비한다. 대안은 scalable Bloom filter다. 1인 비트가 절반에 이르면 더 큰 새 필터를 추가하고, 조회는 모든 필터에 OR로 묻는다. false negative가 없다는 성질은 유지되고, 전체 FP는 등비급수로 묶인다.
