# Week 4 observation

## Task 1
- Bloom filter는 비트를 0→1로만 바꾸므로 넣은 원소의 비트가 꺼질 수 없어, false negative가 구조적으로 불가능하다. 예측 FP 0.860%, 실측 0.865%로 일치했다.
- FM은 해시 64개의 R을 평균한 2^(평균R − 0.333)을 썼다(0.80~1.32배). 2^R 평균(2.06~10.67배)과 교재의 그룹 평균→중앙값(8·16·32개 묶음 모두 과대 추정, 2배 이내 최대 2/10)은 2^R의 무거운 꼬리 때문에 실패했다.
- reservoir는 `j = randrange(i); if j < k` 두 줄에서 i번째 원소를 k/i 확률로 받아, 길이를 몰라도 매 순간 표본이 균등하다.

## Task 2
- i5-12450H·16 GB에서 정확한 set은 'n = 1억'(서로 다른 원소 약 3,670만)에서 시스템 메모리가 14 GB(90%)를 넘어 중지했다. 먼저 바닥난 것은 '메모리'이고(시간은 5~6분 예상), tracemalloc으로 외삽한 값(3.3 GB)의 약 4배였다.
- set 메모리는 n에 비례하고(원소당 89 B = 문자열 60 B + 테이블 칸), FM은 n이 250배가 되어도 4.4 KB로 상수다. 대신 FM 비율은 0.86~1.14배로, 오차는 n이 아니라 해시 개수가 정한다.
- 순사용자 수에 2배 이내 오차는 트래픽 추이 감시에는 충분하지만, 과금이나 몇 % 차이를 보는 A/B 테스트에는 부족하다.

## Task 3
- k만 바꿨다. FP = (1−e^(−kn/m))^k는 p = e^(−kn/m) = 1/2에서 최소이므로 k = (m/n)·ln2 = 6.93 → 'k = 7'.
- 하한은 0.6185^10 ≈ '0.819%'이고, 실측 0.791%로 도달했다(베이스라인 9.511% 대비 91.7% 감소, 하한과의 차이는 표본 오차 범위).
- n을 작게 잡으면 비트가 절반 넘게 차서 FP가 급증하고(실제 n이 2배면 13.8%), 크게 잡으면 메모리를 낭비한다. 1인 비트가 절반에 이르면 새 필터를 추가하는 scalable Bloom filter로 대응한다.
