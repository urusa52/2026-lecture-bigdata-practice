## A2 · 불편해진 지점과 먼저 바닥난 것

- 견딜 수 없어진 크기: 'n = 1억'(서로 다른 원소 약 3,670만). 실행 중 작업 관리자의 메모리 사용량이 최대 약 14 GB(사용 가능한 15.7 GB의 90% 이상)까지 올라가 직접 중지했다.
- 먼저 바닥난 것: '메모리'. 같은 비율이면 n = 2,500만에서 83초였던 시간은 n = 1억에서 약 5~6분으로 예상되어, 시간은 아직 견딜 만한 수준이었다.
- 예측과의 차이: tracemalloc 기준으로는 1억에서 약 3.3 GB(원소당 89바이트 × 3,670만)를 예상했다. 하지만 시스템 메모리는 최대 약 14 GB였다. 다른 프로그램 1.2 GB를 빼면 파이썬이 약 12.8 GB를 쓴 셈이다. 서로 다른 원소당 약 350바이트로, tracemalloc 값(89바이트)의 약 4배다. 이전에 이 값으로 추정했던 한계(n ≈ 3억)는 3배 이상 낙관적이었다. 원인은 다음 두 가지로 추정한다(미검증).
  - tracemalloc은 살아 있는 할당마다 추적 정보를 따로 저장하는데, 여기서는 그 블록이 문자열 3,670만 개다.
  - set이 커질 때 잠깐 옛 테이블과 새 테이블이 동시에 존재한다.
- n = 2,500만까지는 FM이 오히려 느렸다(25분). 원인은 아래 A4에 있다.

## A4 · 증가율

- set 메모리: n이 4배가 될 때 3.0 → 4.0 → 4.0 → 3.95배로 'n에 비례'한다. 서로 다른 원소 하나당 87~89바이트다(100,000에서 115바이트인 것은 고정 오버헤드 때문이다). n = 2,500만의 818.2 MB는 다음과 같이 정확히 분해된다.
  - 문자열: `sys.getsizeof('key-1234567')` = 60바이트 × 918만 개 = 551 MB
  - 해시 테이블: 칸 2²⁴개(채움률 0.547) × 칸당 16바이트(해시 + 포인터) = 268 MB
  - 합계 819 MB, 실측 818.2 MB와 일치한다.
- FM 메모리: n이 250배가 되는 동안 4,428 → 4,430바이트로 '상수'다. 해시 64개의 R 값(정수 64개)과 원소 하나의 256바이트 다이제스트 같은 임시 버퍼뿐이다. 데이터가 아니라 해시 개수가 정한다.
- 시간: 둘 다 n에 비례한다. 원소당 시간은 set이 2.45 → 3.3 µs, FM이 51 → 61 µs다.
  - 이 시간에는 스트림 생성이 포함되므로, set의 3.3 µs는 대부분 원소를 만드는 시간이다.
  - FM은 해시 64개 계산에 원소당 약 57 µs를 더 쓴다.
  - set의 원소당 시간이 조금 늘어난 것은 테이블이 CPU 캐시보다 커졌기 때문으로 추정한다(미검증).

## A5 · FM 정확도

- 비율: 1.14 → 0.86 → 0.96 → 0.98 → 0.95. 'n과 상관된 추세는 없다.'
- 오차를 정하는 것은 n이 아니라 '해시 개수'다. Flajolet & Martin(1985)의 분석에 따르면 최대 꼬리 길이 R의 표준편차는 약 1.87비트다. 64개를 평균하면 1.87/√64 ≈ 0.23비트, 즉 약 ±17%다. 측정값 모두 이 범위(±14%) 안에 있다.
- 크기가 달라도 정확도가 그대로라는 점이 FM의 장점이다. 다만 오차를 절반으로 줄이려면 해시가 4배 필요하고, 그만큼 시간도 늘어난다.
