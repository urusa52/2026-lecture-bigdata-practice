# Week 6 observation

> Task 2는 노트북(i5-12450H)에서 측정했고, 나머지 시간은 클라우드(Linux, Python 3.13)에서 쟀다. 카운터 수는 시드가 고정되어 머신과 무관하다.

## Task 1
- 신뢰도는 비대칭이다. {1468, 0}은 52번 같이 나왔지만 1468 → 0은 0.839, 0 → 1468은 0.004이고, 의미 있는 방향은 드문 상품에서 출발하는 1468 → 0이다.
- 신뢰도 1위 규칙 1468 → 0은 향상도가 1.28뿐이다. 상품 0이 바구니의 65%에 있어 생긴 결과라 믿지 않으며, 향상도 2 이상인 21쌍은 모두 심어 둔 쌍이었다.
- brute force는 C(2000, 2) = 1,999,000개, A-Priori는 pass one 후 1,849개가 남아 C(1849, 2) = 1,708,476개(실제 나온 쌍만 세면 820,259개)의 카운터가 필요하다. support가 낮아 약 15%만 줄었다.

## Task 2
- support 400 → 1(400배)까지 낮췄지만 터지지 않았다(support 1에서 8초, 327 MB, 시스템 메모리 약 300 MB 증가). support 25부터 모든 상품이 빈발해져 카운터가 데이터의 쌍 수 893,456에서 멈췄기 때문이다.
- A4: 카운터는 반으로 낮출 때마다 ×5.54, ×4.67, ×3.00으로 늘었다. 인기도가 Zipf(지수 0.8)라 빈발 상품이 ×2.38씩 늘고, 카운터는 그 제곱(×5.66)을 따른다.
- A5: 답은 ×2.5~3씩 꾸준히 늘어서, 답 하나당 카운터가 support 400의 약 43개에서 50의 128개가 되었다. 임계값을 조금만 낮춰도 답은 3배, 메모리는 5배가 된다.

## Task 3
- 버킷은 2^20개로 정했다. 쌍 등장 343만 번에 대해 버킷 평균(3.3)이 support 50보다 훨씬 작아야 비트맵이 걸러 내기 때문이고, 카운터는 820,259 → 14,337(98.3%)로 줄었다.
- R5: 버킷 배열(4 MB)도 pass one의 메모리라서 최대 메모리는 A-Priori 삼각 행렬(6.7 MB)보다 39%만 줄었고, 절약보다 이동에 가깝다. 버킷 배열은 고정 비용이라 바구니 약 5,000개부터 이기며, 상품이 많을수록(A-Priori ≈ 4·C(k, 2)) 격차가 커진다.
- 버킷을 16,384개로 줄이면 평균이 209가 되어 모든 버킷이 빈발이 되고, 감소율이 0%였다(65,536개는 65%, 131,072개는 91%).

## Task 4 (선택)
- A6: 모든 청크에서 cᵢ < pᵢ·s면 Σcᵢ < Σpᵢ·s = s이므로, 전체 빈발 쌍은 반드시 한 청크 이상에서 후보가 된다. 청크에 s를 그대로 쓰면 6,397개 중 6,034개를 놓쳤다.
- A5: 청크를 2 → 100개로 늘리면 후보는 7,760 → 893,456으로 늘었지만, 답은 항상 6,397개였다. pass two가 전체를 다시 세서 거짓 양성을 지우기 때문이다.
- pass two를 "바구니의 쌍을 후보 집합에서 찾기"로 바꿔 31초 → 0.45초가 되었다(Spark는 설치 실패로 미실행). 단일 머신에서는 느려도, 데이터가 한 머신에 안 들어갈 때 쓸 수 있는 것은 SON이다.
